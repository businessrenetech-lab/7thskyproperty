# Seventh Sky HRM (Modules 1–3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the client's HRM inside the Seventh Sky admin: Organisation Structure, Employee Master Database, and Recruitment & Applicant Tracking. Each change the client lists as needing approval goes through an approval chain, and every change is kept in a history log.

**Architecture:** This is a new HR area. It follows the backend's existing layers: migrations, then models, then pure services (where the rules live, unit-tested with plain `assert` scripts), then thin controllers and routes mounted under `/api/hr/*`. One generic **change-request engine** carries every approval chain the spec lists. It applies a change only after the final approval and writes `hr_history`. The frontend is a new **HR console** (`config/consoles.js` → `ServiceConsole`, base path `/hr`), designed in FigCraft before it is built. It also has employee self-service pages, and public careers and offer pages that work by token without a login.

**Tech Stack:**
- Backend: Node, Express, Sequelize, MySQL (migrations own the schema).
- Frontend: React 18, Vite, recharts, lucide-react.
- Design: FigCraft CLI, using the existing `docs/design/figcraft-kit.js`.

**Spec:** `docs/hrm/requirements-v0.1.txt` (the client's *Seventh Sky CRM – HRM System V0.1*). Section numbers below refer to it, for example M2 §9 means Module 2, section 9.

**Inputs:**
- **Hadi Real Estate HRM code (received 30 Oct 2026).** Its attendance, office calendar, leave, shift planner and ZKTeco biometric modules are already ported and running (migration `0163-hr-attendance-leave-biometric.js`, API `/api/hrm/*` and `/api/biometric/*`, screens `/hr/attendance`, `/hr/leave`, `/hr/shifts`, `/hr/biometric`, `/hr/my-attendance`, `/hr/my-leave`). This plan builds on them (Tasks 9, 11, 14). Task 0.1 maps the rest of Hadi (recruitment and jobs, staff onboarding/offboarding forms) onto Phase 3 before it starts.
- **CRM integration with Hadi.** This is a later plan.
- **Coverage:** `docs/hrm/requirements-coverage.md` maps every spec section to its design window and task.

## Global Constraints

- Hierarchy: `Company → Division → Department → Team → Position → Employee` (M1 §3).
- Scale floor: 10 trading businesses, 50 divisions, 100 departments, 1,000 positions and 5,000 employees (M1 §13). Every list endpoint is server-paginated and indexed on its filter columns.
- Management can add, edit, deactivate and restructure the organisation without a developer (M1 §2, §13). Nothing in the organisation is hard-coded or seeded as fixed.
- Employee ID format `SSPC-EMP-0001`. It is generated automatically and never changes, including on a transfer (M2 §4).
- "No old record should be deleted. Changes must be stored in history log." (M2 §6). Records are deactivated or archived, never deleted.
- "No employee should be created without being linked to: Company, Division, Department, Position, Supervisor" (M1 §10).
- "No employee should appear in attendance, payroll, leave, training or performance modules unless they exist in the Employee Master Database" (M2 §18).
- "No candidate shall be transferred to the Employee Master Database until: offer accepted, mandatory pre-employment checks completed, required approvals obtained, HR confirms onboarding" (M3 §21).
- Payroll and bank details are visible only to authorised HR and Finance users. Managers never see salary or confidential HR records unless authorised (M2 §3.4, §13).
- Sensitive fields are salary, bank account, medical documents, National ID, disciplinary records and personal family information (M2 §10).
- Approval chains (exact):
  - Organisation changes: HR request → HR Manager review → CEO approval → system updated → history log (M1 §6).
  - Employee changes needing **HR Manager** approval: new employee, employment status change, department transfer, position change, supervisor change.
  - Employee changes needing **CEO** approval: salary change, promotion, termination, senior role appointment, sensitive profile changes.
  - Employee changes needing **Finance** approval: bank account change, salary structure update, allowance update, deduction update (M2 §9).
  - Vacancies: Department Manager → HR Manager → Finance Verification → CEO Approval → Vacancy Published, recording date, time, approver and comments (M3 §5).
- CV screening default weights (M3 §11): Education 15%, Relevant Experience 30%, Technical Skills 20%, Communication Skills 15%, Cultural Fit 10%, Certifications 10%.
- Every AI recommendation is reviewable by HR before any action (M3 §20).
- Private documents (CVs, IDs, medical certificates, offer letters) go only under `/uploads/documents`, which requires a login (AGENTS.md).
- Repo rules (AGENTS.md):
  - apply `branchScope` and `pick` to every query and create
  - wrap every controller in `asyncHandler`
  - migrations are numbered from `0164-` (0163 is the attendance/leave/biometric port) and guarded with `describeTable`; never call `sequelize.sync()`
  - parse JSON columns defensively
  - append-only `AGENT_WORK_LOG.md`

## Review Focus

1. **Someone approving their own request.** An HR Manager who raises a change must not also approve it at the HR Manager step; it waits for another HR Manager or the CEO. Tested in Task 3.
2. **Two pending changes to the same thing.** A second salary or position change for the same employee while one is pending is refused with "A change to this is already waiting for approval". Tested in Task 3.
3. **A reporting-line loop.** Making A report to B when B already reports to A, at any depth, is rejected with the chain named. Tested in Task 2.
4. **Deactivating something still in use.** A department or position with active employees or open vacancies cannot be deactivated. The error says how many records block it. Tested in Task 2.
5. **The same applicant applying twice.** A second application with the same email, mobile or National ID attaches to the existing candidate, who keeps their history, and HR sees a "possible duplicate" flag. Tested in Task 17.

### Task 4: HR access control (editable by the CEO)

Decision (30 Oct 2026): the client's tables in M1 §7 and M2 §10 are the **defaults**. The CEO can change them on a "Roles & access" screen. The server always enforces the stored settings. This replaces the legacy, unenforced `rbac_configs` matrix for HR.

**Files:**
- Create: `backend/services/hrAccess.service.js`, `backend/controllers/hrAccess.controller.js`, `backend/routes/hrAccess.routes.js` (`/api/hr/access`), `admin-portal/src/screens/hr/RolesAccess.jsx` (HR console → Insights → Roles & access, CEO only)

**Interfaces:**
- HR roles: `ceo, hr_manager, hr_officer, finance_manager, department_manager, team_leader, employee, it_admin`. They are stored in `users.role`, which is already a STRING. `super_admin` maps to `ceo`.
- `hrRoleOf(user, employee?) → hrRole`. It reads `users.role` first. `ceo`, `hr_manager`, `hr_officer`, `finance_manager` and `it_admin` are role strings. Anyone else linked to an `hr_employees` row is `employee`, or `department_manager` / `team_leader` when the org structure names them manager or leader of a department or team (relationship, not a role string). `super_admin` maps to `ceo`.
- `DEFAULT_MATRIX` and `DEFAULT_FIELD_GROUPS` hold the client's tables. `loadSettings()` merges the stored `hr_access_settings` over the defaults, cached for 60 s and cleared on save.
- `can(hrRole, action, settings = defaults) → boolean`. The actions are:
  - `org.view_basic`, `org.edit`, `org.view_cost`
  - `emp.view_any`, `emp.view_team`, `emp.view_own`, `emp.edit`, `emp.view_payroll`, `emp.view_sensitive`
  - `rec.manage`, `rec.request`, `approvals.inbox`
- The matrix comes from M1 §7 and M2 §10. For example, `it_admin` gets `emp.view_any` but not `emp.view_payroll`, and `finance_manager` gets `emp.view_payroll` and `org.view_cost`.
- `maskEmployee(employee, viewer: { hrRole, employeeId, teamIds[] }) → object`. Fields the viewer may not see are removed, not set to null.
  - The payroll group is basic_salary, allowances, bank fields, mobile banking, tax status, provident fund, loan balance and deduction rules.
  - The sensitive group is national_id, passport, medical documents, disciplinary, family.
  - Export and every list endpoint use this same function.
